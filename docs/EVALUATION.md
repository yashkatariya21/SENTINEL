# Evaluation

Three different things get measured here. They answer different questions and must never be quoted
interchangeably.

| What | Command | Needs a key? | Question it answers |
|---|---|---|---|
| Behaviour tests | `cd backend && pytest -q` (66 cases) | no | Do the deterministic rules, permissions and tenancy boundaries hold? |
| **Pipeline regression benchmark (rule-based engine)** | `python -m eval.run_eval` | no | Did a rule or code change break the engine's behaviour on the tuning set? |
| **Held-out adversarial set** | `python -m eval.run_eval` (same run) | no | Does the engine generalise to copy it was not tuned on? |
| **LLM evaluation** | `python -m eval.run_llm_eval` | **yes** | How well do three prompt configurations perform, at what latency and cost? |

The in-app `/evaluation` page renders whatever is on disk. If a report is missing, the page says
"not measured" — it never shows a placeholder score.

## 1. Pipeline regression benchmark (rule-based engine)

> **Naming matters.** This benchmark was previously described as an "evaluation". It is a
> regression check. It is **not** a measurement of LLM quality, and the single-prompt comparison in
> it is a keyword sweep, not an LLM.

`backend/seed/samples.py` holds **53 hand-written samples** for the fictional Northwind Analytics
workspace, each with human-labelled spans:

* 8 samples are **deliberately clean** (no seeded mistake) — they exist only to measure false positives.
* Mistakes cover all six reviewers: banned terms (`cheap`, `utilize`, `Leverage`, `ForecastCloud`),
  hype (`revolutionary`, `world-class`, `seamless`), risky claims (`Guaranteed results`, `100% safe`,
  `best company`, `risk-free`), wrong numbers (`98%` renewals vs the approved `87%`, `£18` vs `£24`),
  unsupported numbers (`3.2 million customers`, `42% faster`), accessibility issues (`12pt`, `10px`,
  `click here`, ALL-CAPS blocks, colour-only instructions) and visual issues (off-palette hexes,
  retired logo versions).

### The circularity, disclosed

**The samples and the rule pattern lists were written together by the same author.** A reviewer
that matches a pattern will usually match a sample that was designed around that pattern. That is
why the regression number is high, and why it is the *least* interesting number on this page. It is
still useful — it catches regressions — but it says nothing about unseen copy.

### Scoring rules (identical for every experiment here)

* **True positive** = same reviewer *and* span overlap with the label at IoU ≥ 0.3; each label matches once.
  If a reviewer produced no findings at all, precision is displayed as `—`, not `1.00`.
* **False-positive rate** is sample-level: share of samples with no seeded mistake for that reviewer that
  still received a finding. That is the "crying wolf" number a brand team actually feels.
* **The baseline** (`backend/eval/baseline.py`) is a deterministic flat keyword sweep: one pass, no
  per-reviewer job description, no mandatory rule citation, no evidence lookup, no span merging. It is
  a proxy for *architecture* (does splitting the job six ways help?), **not** for a model. Nothing in
  this repository should call it an LLM.

### Manager-approved exceptions

The benchmark runs with `honour_exceptions=False`. It measures how well the reviewers read the written
brand rules. Manager-approved exceptions are the organisation's later policy decisions: they are applied
in the running app and exercised by the regression run that fires after every promotion, but they must
not flatter or distort this score.

## 2. Held-out adversarial set — the honest number

`backend/seed/heldout_samples.py` holds **20 samples written after the rules were finished and never
used for tuning**: near-miss clean copy that must stay unflagged, paraphrased violations that avoid the
obvious keywords, and hostile inputs (instruction-like text, zero-width characters, a two-word body, a
French paste).

Measured on the same run as the table above:

| Scoring | Precision | Recall | F1 |
|---|---|---|---|
| strict — correct reviewer *and* span overlap | **0.29** | **0.26** | **0.27** |
| relaxed — any reviewer covering the labelled span | 0.52 | 0.48 | 0.50 |

Mean sample-level false-positive rate across the six reviewers: **0.06**.

**Read that plainly:** the rule engine reproduces its tuning set almost perfectly and generalises at
roughly half that. The strict number is also harsh by design — flagging the right span with the wrong
lens scores zero, which the relaxed row (0.50 F1) shows explicitly. Six of the twenty samples were
clean; the engine stayed quiet on five of them.

Every miss is listed on `/evaluation` and in `backend/eval/report.md`. Closing this gap is exactly what
the hosted-LLM configuration is for, and that is measured separately below — with real calls, or not
at all.

## 3. LLM evaluation

`backend/eval/run_llm_eval.py` runs three configurations over the same samples, with the same matching
rules, temperature 0, a fixed seed and a disk cache keyed on
`(provider, model, prompt version, config, text hash, seed)`:

| Configuration | What it isolates |
|---|---|
| `single_prompt` | One generic prompt asking for every issue at once. No per-reviewer job, no rules, no citations. |
| `six_reviewers` | Six specialist prompts, one call each, no retrieved rules. The value of splitting the job. |
| `full_context` | The product configuration: six specialists **plus** retrieved rule text and approved facts, citations required. |

Measured per configuration: precision / recall / F1 (micro and per reviewer), false-positive rate,
latency p50 and p95, prompt and completion tokens, and estimated cost at published list prices.
Results are written to `eval/report_llm.md` and `eval/report_llm.json`.

**With no key it exits with status 2 and prints instructions.** It does not print expected, sample or
placeholder numbers — with no key there is no measurement.

```bash
cd backend
export LLM_PROVIDER=openai LLM_API_KEY=sk-... LLM_MODEL=gpt-4o-mini
python -m eval.run_llm_eval                 # all three configs, both sample sets
python -m eval.run_llm_eval --no-cache      # fresh calls, real latency
```

> **Status in this repository: not measured.** No key was configured when this build was produced, so
> there is no `eval/report_llm.json` committed. The harness's plumbing (prompt construction, parsing,
> metrics, token accounting, latency percentiles, caching) was verified against a local stub endpoint
> during development; those stub numbers were discarded and are not reported anywhere, because they
> measure the stub, not a model.

## What is *not* measured

* Human-agreement studies (inter-annotator agreement on the labels).
* Production traffic, or performance against a customer's own Brand Kit.
* Prompt-injection resistance under adversarial grading (the pipeline detects instruction-like text and
  the behaviour test covers it; there is no scored adversarial suite).
* Cost of the deterministic engine — it is zero by construction, so there is nothing to measure.

Two failures are visible rather than hidden: the held-out gap above, and the reviews in `report.md`.
A demo that shows only wins is a demo, not an evaluation.
